# 视觉诊断与迭代

目标是找到可执行的修复，不是给游戏一个看似精确的总分。用户的参考和目标优先；缺乏目标时先根据当前游戏提出可检查的视觉约定。

## 建立证据

记录可复现的入口、场景或资产、机位、输出尺寸、随机 seed、时间或动画状态。复用项目已有测试入口；必要时增加轻量展示页或调试控制，不要求每项任务建设测试框架。

基线与候选使用相同条件。切换到新的机位、曝光、分辨率或状态时标明差异，避免把它们混入造型改善的结论。动态问题看过程，不只看终点。

实际读取工具返回的图像。无法运行或无法看图时，可以完成可检查的代码工作，但交付需区分“代码已实现”“运行已验证”“视觉已检查”，不能把三者混为一谈。

## 诊断顺序

| 现象 | 优先检查 | 不要直接下的结论 |
| --- | --- | --- |
| 像占位模型 | 轮廓、比例、分件、厚度、观察角度 | 多加纹理就能解决 |
| 所有表面像塑料 | 材质参数、反射环境、光照、曝光、色彩空间 | 所有贴图都要重做 |
| 画面很乱却没有重点 | 明度层次、主体尺寸、装饰分布、特效遮挡 | 内容还不够多 |
| 近看刺眼，远看没细节 | 细节频率、纹理过滤、屏幕覆盖面积 | 只需更高分辨率 |
| 物体漂浮或纸片感 | 接触、厚度、阴影、法线、比例 | 增加 Bloom 或全局变暗 |
| 截图不错，运动时很差 | 枢轴、挂点、时间步长、闪烁、动画过渡 | 静态验收已经通过 |
| 一套资产像来自不同游戏 | 形体语言、色板、比例、材质与细节尺度 | 每个资产单独好看即可 |

这些是排查方向，不是仅凭截图就能确认的原因。可以临时隔离纹理、反射或后处理作诊断，但不要把诊断状态遗留在成品中。

## 最小迭代记录

适用于多轮工作；单次小改动不必创建独立文件。

```text
观察：游戏镜头中，主体右侧与地面融合，轮廓不清。
假设：两者明度接近；先排除曝光与法线异常。
修改：调整主体与环境的明度关系，保持材质结构和镜头不变。
复查：比较同机位图，再看转向过程中轮廓是否持续清楚。
结果：记录实际改善、剩余问题、回归；保留或回退本轮变化。
```

每轮优先处理少数高影响问题。截图差异只能说明像素变化，不说明质量提升。模型自评可以提供线索，不能替代图像证据、功能验证或实际性能采样。

## 迭代停滞时

- 先检查是否读到了更新后的画面、热更新或缓存是否生效、所改对象是否实际出现在场景。
- 再检查诊断是否过于笼统；把“更精致”拆到某个区域、形体关系或材料响应。
- 将大任务缩为一个资产或一种材质，在可控展示条件下验证，再放回游戏。
- 按需检索相关案例或采用项目可用的替代实现。只有环境和授权允许时才调用其他模型或代理；本 Skill 不要求多 Agent。
- 用户限制纯代码时，在该限制下改变构造或渲染方法；若目标仍无法达到，保留最佳实现并说明差距，不擅自换成外部资产。

## 完成依据

同时考虑：与约定风格和观看方式一致；关键轮廓与交互可读；几何、材质和动画无明显新增缺陷；接入正常；新增成本在已知预算内。

报告哪些视角、状态和设备实际检查过。静态画面检查不是完整试玩，开发机表现不是所有设备表现，精选截图不是对整款游戏质量的证明。
